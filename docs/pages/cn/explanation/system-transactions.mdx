# 系统交易

Stable 使用**系统交易**将 SDK 模块事件转换为标准 EVM 日志。应用程序可以通过 `eth_getLogs` 或现有的 WebSocket 订阅来消费这些日志。

例如，在 Staking 模块完成解绑操作后，系统交易会发出 `UnbondingCompleted` 事件。该事件包括委托人、验证人、原始完成高度和金额。

## 应用程序接收到的内容

考虑跟踪用户代币何时完成解绑。如果没有系统交易，dApp 需要：

- 运行一个单独的索引器，监听 SDK 事件并将其存储在自己的数据库中。这会增加操作开销并引入新的故障点。
- 定期轮询 REST 端点。这会导致 5-10 秒的延迟，更高的 RPC 负载，以及需要维护两个客户端堆栈（web3 + REST）。

系统交易通过 dApp 已经用于 EVM 日志的相同 WebSocket 连接提供实时事件通知。无需单独的索引器。无需 REST 轮询。

## 工作流程

```text
1. 协议事件：    SDK 层操作完成（例如，staking 解绑）。
2. 检测：         x/stable EndBlocker 检测到该事件并将其排队存储。
3. 系统交易：     在下一个区块的 PrepareProposal 中，协议生成一个
                      系统交易，调用 StableSystem.notifySystemTxLogs()。
4. EVM 发射：      预编译处理排队的条目并发出标准的
                      EVM 事件。dApp 通过 eth_getLogs 和订阅查看它们。
```

系统交易由验证人在区块提案期间创建，而不是由用户创建。它位于区块的开头，在任何用户交易之前。

## `StableSystem` 预编译

事件通过 `0x0000000000000000000000000000000000009999` 处的 `StableSystem` 预编译流转。目前，它发出 `UnbondingCompleted` 事件，其中包含委托人、验证人、原始完成高度和金额。

相同的预编译暴露了公共的 `blockspaceLanes()` 视图方法。它返回用于链下交易分类的活动 Enterprise 和交易类型通道注册表。

## 安全模型

两个属性使事件流值得信赖：

- **仅协议发送方。** 系统交易使用 `0x0000000000000000000000000000000000000001` 作为其发送方。EVM 状态转换规则为协议生成的交易保留此地址。用户无法伪造事件或从自己的交易中调用 `notifySystemTxLogs()`。
- **确定性发射。** 每个诚实的验证人都会为相同的协议事件生成相同的系统交易。除了标准共识之外，没有额外的信任假设。

## 批量处理

为了限制区块大小，每次调用最多处理 100 个排队的系统日志条目。如果突发事件超过限制，剩余的条目将继续排队等待后续区块。

SDK 事件和 EVM 发射之间存在一个区块（约 700 毫秒）的延迟，相对于 7 天的解绑周期而言，这是可以忽略不计的。
